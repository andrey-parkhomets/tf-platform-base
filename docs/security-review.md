# Security review against the action's own guidance

I went through `anthropics/claude-code-action` `docs/security.md` point by point. This table describes the comment-driven design (`agent-commands.yml`). It adds one row at the end for the push credentials.

| Guidance | What this repo does | Residual / note |
|---|---|---|
| Only users with write access can trigger it | The `gate` job checks the commenter's repository permission (`admin`, `maintain` or `write`) with the API before anything else, and ignores bot authors. The action's own actor check still applies. Fork pull requests are refused with a comment: the agent cannot push to them and their code must not run next to a secret | A collaborator with write access is trusted. That person can also edit the workflow itself |
| Bots cannot trigger it unless `allowed_bots` is set | Not set. Comments by bots never match (`user.type != 'Bot'`) | |
| Do not check out untrusted refs under `pull_request_target`/`workflow_run` | The agent workflow uses `issue_comment`, which has the same property as `pull_request_target`: it runs with secrets, from the default branch. That is why it is gated by write permission, same-repository only, and a strict one-line command grammar (`parse-command.sh`, tested). The pull request's code is checked out with `persist-credentials: false` and executed only in the `agent` job (model key scrubbed from subprocesses) and the `verify` job (no secrets). `terraform-checks.yml` stays on `pull_request` | A write-access user who is also a malicious author can still put hostile Terraform in a same-repository branch. That risk is the same as before and is bounded by the scrub, the sandbox and the no-secret verify job |
| `.claude/` etc. are restored from the base branch | The `agent` job copies `.claude/` and the helper scripts from the default branch over the pull request's checkout, commits that as a local baseline, and every later guard compares against it. It does not rely on the action's own restore, which was written for `pull_request` events | A change to the agent or the skills takes effect after it is merged |
| Repo-relative scripts, hooks and package-manager commands resolve through PR-controlled files | The agent is **not** allowed to run `pre-commit` (its config is PR code) or any repo script. The only helper it may run, `check-test-quality.sh`, is copied from the **base commit** to `$RUNNER_TEMP` and called by absolute path. There are no hooks, `apiKeyHelper` or `statusLine` in `.claude/` | `terraform test` still executes provider and module code from the PR; see the next row |
| Subprocess environment scrub (`CLAUDE_CODE_SUBPROCESS_ENV_SCRUB`) | Set to `1` for the agent step. Verified locally: with it on, a subprocess started by the agent cannot read `ANTHROPIC_API_KEY` or cloud keys; off, it can. It needs bubblewrap and socat, installed and tested by a workflow step that fails with a clear message if the runner cannot create a sandbox. Repository variable `AGENT_SUBPROCESS_SCRUB=0` relaxes it deliberately | `GITHUB_TOKEN` (read-only, expires with the job) remains readable by subprocesses |
| No long-lived tokens for the action | `github_token: ${{ github.token }}` with `contents: read`; no PAT | |
| `show_full_output` / step debugging print everything, publicly on public repos | `show_full_output` and `display_report` are off; a step fails the job when `runner.debug == '1'` instead of printing the agent's full output | Do not set the `ACTIONS_STEP_DEBUG` secret |
| Prompt injection from untrusted content | The PR title and body are not given to the agent. The agent file and skills say that diff content, comments and Checkov output are data. Tool allow-list, path guard, and a separate no-secret verify job bound the damage. Tested with a real injection attempt in the diff (see `docs/model-comparison.md`) | Not a proof. The guard and allow-list are the controls that do not depend on the model behaving |
| Never hardcode keys | A local pre-commit hook rejects `sk-ant-...` strings; keys live in GitHub secrets, and the git-ignored `.secrets` file for local runs. An earlier key was pasted into a chat during development, so it was treated as exposed and replaced | |
| Commit signing, PR creation | The model never commits and never opens pull requests. The `commit` job commits as the GitHub App (commits made through a git push with an App token are not signed). Branch protection that requires signed commits would need the App to sign through the API instead | Listed under production changes |
| `CLAUDE_CODE_SCRIPT_CAPS` for write-capable helper scripts | Not used: the only helper script the agent may call is read-only | Worth adding if a write-capable helper is ever added |
| Push access | A GitHub App installation token (`actions/create-github-app-token`, `contents` and `pull-requests` write only, valid one hour) is created only in the `commit` and `remove` jobs. Those jobs run no model and no Terraform; they apply a patch that `verify` accepted after re-checking its paths (`commit-patch.sh`), or revert a bot-authored, test-only commit (`revert-commit.sh`). Pushes are never forced. A push by the App starts the normal `pull_request` checks, which a `GITHUB_TOKEN` push would not | The App's private key is a long-lived secret. The App can push to any branch of the repository it is installed on, so install it on this repository only and keep branch protection on `main` |
